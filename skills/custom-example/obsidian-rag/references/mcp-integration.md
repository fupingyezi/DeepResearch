# obsidian-rag MCP 集成与时序

## 服务与 MCP 的关系

`obsidian-rag` 是一个本地项目（本示例模板不内置路径，脚本读 `OBSIDIAN_RAG_DIR` 环境变量）：

- `npm run ask -- "问题"` —— 一次性 CLI 问答，进程随回答结束自行退出（本 skill 的主查询路径）
- `npm run mcp:http` —— 常驻 HTTP MCP server，默认 `127.0.0.1:3333`，即应用配置里 `obsidian-rag` MCP server 的 URL

两者共用同一份索引（`DB_PATH`）与同一套检索管线，答案质量一致；区别只是入口形态。

## MCP 工具加载时序（决定 serve/kill 策略的关键）

应用里 MCP 工具的加载语义：

- **每轮对话开始时**加载一次启用 MCP server 的工具（`loadMcpTools()`，按启用配置签名缓存）
- 连接失败**不会写入缓存** —— 服务没起时本轮静默无工具，下一轮对话会重试
- 因此：`rag-serve.sh` 在本轮对话中途启动服务，**本轮**拿不到 MCP 工具（工具集在对话开始已定型），但**后续每轮对话**都能在开始时直接加载到

## 推荐策略

| 场景                 | 动作                                                                   |
| -------------------- | ---------------------------------------------------------------------- |
| 偶尔问一句笔记       | 只用 `rag-ask.sh`，不起服务                                            |
| 本轮多次查询         | `rag-ask.sh` 逐条问；服务可起可不起                                    |
| 用户近期会频繁问笔记 | `rag-serve.sh` 保持常驻，后续对话直接用 MCP 工具；不用时 `rag-kill.sh` |
| 问完即收工           | `rag-kill.sh` 收尾（端口与空闲资源释放）                               |

服务本身很轻（本地 SQLite + 外部 API 调用），常驻的开销只是占一个端口；默认建议**问完就 kill**，避免遗忘。

## MCP 工具可用时的选择

后续对话若 MCP 工具已加载（工具列表里可见 `obsidian_rag_*`），直接用 MCP 工具即可，不必再跑脚本；工具不存在时回落 `rag-ask.sh`。两者不混用（同一对话内保持一致即可）。
